# Release notes

Every user-visible change gets an entry here. This page is the changelog customers read, so it is written in product language — what changed for them, not which class was refactored.

## How entries get written

The rule: **the release-note entry lands in the same commit as the feature.** Not a sweep before a release, when the detail has evaporated and someone is reverse-engineering a month of commits from git log.

1. Build the feature.
2. Add a bullet under **Unreleased** below, in the right category.
3. Update the relevant documentation page and its status in the sidebar manifest.
4. Commit all of it together.

At release time, **Unreleased** is renamed to the version with a date and a fresh Unreleased block goes on top. No archaeology required.

### Categories

- **Added** — new capability
- **Changed** — different behaviour in something that already worked
- **Fixed** — a defect
- **Removed** — a capability taken away
- **Security** — anything affecting authentication, authorization or data isolation

### What earns an entry

Anything a user or an administrator would notice: a new screen, a changed rule, a new field, a different default. Internal refactors, test additions and documentation-only edits do not.

Breaking changes are prefixed **⚠ Breaking** and say what to do about it.

### Security
- **Sales documents were relying on a single layer of branch isolation instead of two.** Every table in the sales schema is meant to be guarded twice: a filter in the application that scopes every query to the branch you are signed in to, and a policy in the database that refuses anything that gets past it. ### Added

The distinction matters: a void says the order should never have existed, and voiding one that actually shipped goods would withdraw the document those four units went out on. A reason is required, and it is what tells a closed order that was *fulfilled* apart from one that was *stopped* — the delivered quantities alone cannot say which. If the stock cannot be released the close is refused rather than recorded, because an order marked closed while still holding stock is stock nobody can sell and no document explains.
- **Stock availability, on the order screen.** A **Stock** button opens a drawer showing, per item, what is on hand, what is reserved, and what is actually available — with any line that is short of availability flagged before you try to confirm. **Reserved is not subtracted from on hand**, and the drawer says so: the goods are still on the shelf and still in the valuation, they are promised to a confirmed order. It is labelled as a snapshot, because another till can confirm the last unit while it is open; the check that decides is still the guarded reservation taken on confirm.

- **UTGST is now charged where it is due.** A branch trading from a Union Territory without a legislature — Chandigarh, Lakshadweep and the rest — charges **CGST + UTGST** on its local supplies rather than CGST + SGST. Same rate and the same half, and it lands in the same State/UT column your return has a single field for; what changes is the name printed on the invoice, which is what a customer's own accountant checks. Supplies *out* of the territory are unaffected and still carry IGST. Turn it on with the Union Territory flag on the branch.

- **The invoice list shows what has actually been paid.** Each posted invoice carries **Paid**, **Part-paid** or **Unpaid**, with the amount still due beside a part-paid one — read from the ledger rather than stored on the invoice, so it cannot drift from what the accounts say the moment a receipt is undone. A draft shows nothing at all rather than "Unpaid": it has never posted, so it is not money anybody is owed, and listing it beside invoices you are chasing would pad the collections list with documents nobody can collect on. An invoice a few paise short after a foreign-currency receipt counts as paid, because it is.
- **A printable tax invoice**, from the invoice screen. It carries what an Indian tax invoice has to carry — both GSTINs, the place of supply, HSN per line, and the tax split shown **per rate rather than per component**, which is what a return needs and what a single "CGST 9%" line gets wrong the moment a bill mixes slabs. The total is spelled out in words with Indian grouping (lakh and crore), rounded from the same figure it prints beside so the two cannot disagree. A draft prints watermarked **PROFORMA** and a voided one prints **VOID** — a draft handed over as a tax invoice is a document somebody may try to claim credit on. Note that this is the browser's print, not yet the archived PDF/A copy.

- **Invoices are now a screen you can use** — Sales › Invoices, the document the sale actually happens on and the one your GST return is filed from. A list that pages on the server, filters by status, searches by invoice number and narrows to **overdue**, showing how many days late each one is. **Preview entry** shows exactly what posting will write to the ledger — which accounts, which direction, how much — before you commit to the irreversible step, and it is produced by the same code that does the posting, so it cannot drift out of step with the entry it predicts. **From an order** turns a confirmed sales order into an invoice: the lines are read from the order on the server rather than sent by the screen, and the tax is recomputed at the invoice's own date, so an order taken in March and invoiced in June is charged at June's rates. Only a confirmed order can be invoiced — an unconfirmed one is holding no stock — and one order becomes at most one invoice. The whole screen works down to about 360px.
- **The invoice list totals the page you are looking at, and says so.** The list pages on the server, so a running total across every match is a different query; a figure labelled "outstanding" that quietly covered one page is the kind somebody reconciles against and finds short.

- **Sales orders are now a screen you can use** — Sales › Sales orders, the document that commits a customer's order and **holds its stock back**. It has a list of its own that pages on the server, so a branch with ten years of orders opens as fast as one with ten weeks, and it can be filtered by status and searched by order number. **Confirm & reserve** asks Inventory to hold every stock line: if something is short the order stays a draft and the message **names the items**, rather than saying "insufficient stock" on a twenty-line order and leaving you with nothing to tell the customer. **From a quote** turns an approved quote into an order — the lines are read from the quote on the server rather than sent by the screen, and the tax is recomputed at the order's own date, so a quote priced in March and converted in June is charged at June's rates. One quote becomes at most one order, so a double-click cannot raise two. Voiding gives the reservation back, and is refused outright if Inventory cannot release it — a voided order still holding stock is stock nobody can sell and no document explains. The whole screen works down to about 360px.
- **Business rules and field errors are now shown in different places, everywhere they appear.** A constraint on a field — required, too long, out of range — is shown on that field, where your eye already is. A rule about the document — not enough stock, the credit limit, "a posted document is never edited" — goes to a message box at the top, because no single field is wrong and pinning it to one would be a guess. The box shows the rule's **own words** rather than "operation failed", which is the only part you can act on.

- **Quotes are documented**, and the screen now works on a phone. Sales › Quotes had no page in this documentation and no mobile layout; the list becomes one card per quote and the form stacks to a single column at around 360px, which is the width the rest of the product is built to.

### Fixed
- **The invoice screen would have stopped working the moment anything else registered its service.** The controller had two constructors, and it only worked because exactly one of them could be satisfied; the framework refuses an ambiguous one outright, so every invoice request would have failed at runtime with a message about constructors rather than about invoices. Collapsed to one.

- **No sales document could be saved at all — quote, order, challan, invoice or credit note.** Every one of them failed the moment it had a line on it. The five tables that hold document lines had been wired to their headers twice by accident, once correctly and once by a column the system invented for itself, and lines were being filled into the invented one — leaving the real link empty and the save rejected by the database. It went unnoticed because nothing had yet written to these tables: the sales screens were built against an API nobody had successfully saved through. The duplicate columns are gone and there are tests that fail if one comes back.
- **A sales order could never be withdrawn.** Voiding one asked whether anything downstream pointed at the order, and the check accidentally asked whether the order itself existed — which it always does — so every void was refused as having documents beneath it. It now checks for the invoices and delivery challans that actually point at it.
- **Approving or withdrawing a quote or a delivery challan was impossible for everyone, whatever their role.** Both were asking for a permission that does not exist and cannot be granted, so the answer was always no. They now ask for the ones your roles actually carry.
- **A brand-new sales order was recorded as though it had already been confirmed.** Drafts were being stamped with the time and user of a confirmation that had not happened, which is what tells an abandoned draft apart from an order that was live and then withdrawn.

- **The quote screen showed a total of zero.** Amounts and quantities were handed to the line grid in the wrong units, so a line of 10 at ₹100 came to nothing and a priced quote read as an empty one. It now goes through the same conversion the delivery challan uses.

A list beside the form, and both wired into the app: the form had been written but never given a route, so it sat in the product invisible to anyone using it. ### Added
- **Reports** — a new Reports section, and the grid every report in the product will run in. Two reports open it: **Account Movement**, every posting against every account in date order, and **Trial Balance**, every account with its debits, credits and balance. What matters more than the two is that they behave identically, and so will the forty-three that follow: filter by any column with the operators that column's type actually supports, sort by up to five columns with Shift-click, group up to three levels deep with a subtotal on each, choose and reorder the columns, and export the lot to Excel. **Subtotals and totals are computed over the whole result rather than the page you are looking at**, so a subtotal is right even when its group runs across a page boundary — the thing people quietly re-derive by hand when a report gets it wrong. The export carries every row the filters allow, not the page on screen, with the header frozen and amounts as numbers your spreadsheet can total; it is capped at 100,000 rows and refuses with the count rather than truncating, because a file missing its last rows looks complete. Your columns, filters, sorting and grouping live in the address bar, so a link opens the report somebody else was looking at and a refresh keeps your layout. On a phone each row becomes a card. Two things to know: **PDF export is not built**, and a report the branch's catalog has not been seeded for will not appear — seeding adds only what is missing, so it is safe to run again.
- **Debit notes** — Purchase › Debit notes, the way back out of a purchase. Raise one against a posted bill to reduce what a vendor is owed and reverse the input tax you claimed. **The reason decides whether stock moves**: a *purchase return* sends the goods back, while a price correction, a post-purchase discount, a shortage or a cancellation change the money while the goods stay on your shelf — moving stock for an overcharge would take away inventory you still have. Lines are picked off the bill, each showing how much is still returnable, and prices come from the bill because a credit has to match what was charged. **The same goods cannot be credited twice**: a line already returned in full is not offered, and returning more than was bought is refused. Returned stock leaves at what the layers it came from were carrying rather than at the billed price, so the stock ledger and the accounts agree about what left. A posted purchase return cannot be voided — the stock has gone; a money-only note can be.
- **A Purchase Returns account** is now seeded into every branch's chart of accounts as a *contra* expense, so returns reduce what you bought instead of appearing as a negative expense that reports would add rather than subtract.
- **Bills** — Purchase › Bills, completing the purchase chain: an order commits nothing, a receipt puts stock on the shelf, and a bill clears what the receipt opened and owes the vendor. **Attaching a goods receipt changes what posting does**: the goods are already on the shelf, so the bill moves no stock and clears Goods Received Not Invoiced instead; with no receipt attached the bill brings the goods in itself. The vendor's own bill number is required, because input tax credit is claimed against theirs rather than ours — and **the same vendor cannot bill the same number twice in a financial year**, which is refused as you type it rather than surfacing later as a duplicate claim. Expense lines post to the account you name and capital lines to Fixed Asset without moving stock. Due dates come from a payment term or are set directly, and the list has an overdue filter with a running total for a payment run. Payables are recorded against the vendor, so aging groups by who is owed. One case is deliberately refused: **a bill priced differently from the receipt it bills**, because how that difference is treated is not decided yet — correct the price or detach the receipt.
- **A Fixed Asset account** is now seeded into every branch's chart of accounts, so a capital line on a bill has somewhere correct to land. When the fixed asset register is built, each category will carry its own accounts and this becomes a grouping rather than the destination.
- **Goods receipts** — Purchase › Goods receipts. Record what a vendor actually delivered, against an order or on its own, and post it: the accepted quantity goes into stock at what it cost, the ledger takes *Dr Inventory / Cr Goods Received Not Invoiced*, and the order moves toward closed. **This is the first document in the product that puts purchased stock on the shelf** — until now stock could only arrive through an opening balance. You key what was *rejected* and the rest is accepted; a rejection needs a reason, and rejected units stay owed on the order rather than closing it. Batch and expiry are captured on the line as the cartons are unpacked, and Inventory refuses the receipt by name if a batch-tracked item arrives without one. No GST is posted at receipt — input credit is claimed against the vendor's invoice number, so the tax arrives with the bill. A posted receipt cannot be voided, because voiding cannot un-receive goods; send them back with a debit note instead. If posting fails partway the receipt stays a draft and can simply be posted again without recording the stock twice. One thing to know: **nothing clears Goods Received Not Invoiced yet**, because bills are not built — that balance will grow with every receipt until they land.
- **A GST rate can now be chosen on a document line.** Every sales and purchase line grid gains a rate selector beside the tax treatment. Until now there was nowhere to put a line on a tax group, so lines carried no tax at all — this is the fix, and it applies to the sales screens as much as the new purchase one. Only rates flagged for the document's side are offered, so a sales-only rate does not appear on a purchase order. Choosing a rate splits it into CGST + SGST or IGST according to the document's place of supply, the same rule the server applies when it recomputes the figures on save.
- **Picking an item no longer depends on whether free-text lines are allowed.** The "pick an item" control was only shown when a branch permitted lines without an item — exactly backwards, so a branch that requires an item on every line got a description box it was not allowed to use and no way to choose an item at all. The description is now what that setting controls; picking an item is always available.
- **Purchase orders** — Purchase › Purchase orders, the first screen in the purchase module. Raise an order against a vendor, line it up with the same grid every sales and purchase document uses, approve it, and issue it to the vendor. **An order reserves nothing and posts nothing**, which is the one thing worth knowing if you already use sales orders: a sales order holds stock back when you confirm it, because the goods are on your shelf and could be promised twice. A purchase order has nothing to hold — the goods are not here, which is why you are ordering them. Approving and issuing need the *purchase.approve* permission rather than *purchase.edit*, so committing the company to a spend is a separate authority from keying the paperwork; a branch that does not want the review step can issue straight from a draft. Orders are never deleted — voiding one keeps its number and its reason on record, and an order a receipt already points at cannot be voided at all. One thing to watch: a vendor who is unregistered or on the composition scheme has no GSTIN, so on those orders the place of supply has to be set by hand or the order is refused. Without a GSTIN or a stated place of supply there is no way to tell CGST + SGST from IGST, and guessing produces a document that prints and totals correctly and is wrong on the return. Goods receipts and bills are not built yet, so nothing can be received against an order today.
- **A Goods Received Not Invoiced account** now appears in every branch's chart of accounts, seeded alongside Accounts Payable. It is the clearing account for stock that has arrived without its bill: the goods receipt debits Inventory and credits this, and the bill clears it against Accounts Payable. Its balance is therefore goods on the shelf that no vendor has invoiced yet — a number worth watching at a month end. Branches created before this release pick the account up automatically; the seed adds only what is missing. Nothing posts to it yet, because goods receipts are not built — the account is in place first so that the first receipt ever entered lands somewhere correct rather than needing a chart-of-accounts change underneath it.
- **Contact person roles now have a Settings page**, beside payment terms and the other masters — the same list that already opened as a popup from the contact form. The popup stays, because it exists so a missing role can be added without abandoning a half-typed contact; what it did not do is give anybody setting a branch up somewhere to find the master. Both show the same list, so there is one place to change how it behaves rather than two that drift.
- **Closing dates** — Settings › Closing dates, for shutting the books once a period is done. There is one date **per role**, which is the point of it: a close is rarely all-or-nothing, so the month shuts to everyone who keys documents while staying open to whoever has to make the adjusting entries the close itself produces. One date for the whole branch would close the books on the person doing the closing. The date is inclusive, and a role with no date is not closed at all — a branch that has never closed a period carries no restriction. What is refused is only what reaches or leaves the ledger: posting, reversing, voiding, never the keying, so somebody catching up on last month's paperwork can still type it and finds out when they post. Moving a date earlier reopens a closed period and the screen says so before you save it. The rule behind all of this was already enforced on every posting path; until now there was no way to see or set it.
- **One line grid for every sales and purchase document.** `bb-document-line-grid` in `libs/shared/ui-components` — all nine document types share one line shape, so they share one grid rather than nine near-identical ones. It fetches nothing: lines go in, recalculated lines come out, and the host page opens its own item picker. Amounts are held in integer paise because JavaScript has no decimal type and money that ties to a ledger cannot be computed in floating point. The arithmetic sits apart from the component and is covered by nine tests — writing them found a real bug in the MRP-inclusive back-out, which had been dividing by the rate scale where the rate is a percent and so made every inclusive line a hundredth of its true taxable value.
- **Three document settings on Settings › Organization**, beside the base currency and the financial-year start. **Lines without an item** lets a sales or purchase line stand on a description, quantity and price with no item behind it — useful for a service or a one-off charge, at the cost that such a line moves no stock and never shows up in a sales-by-item report. **Discount entered at** chooses whether a discount is keyed on the line, on the header, or both; a header discount is apportioned across the lines before tax, because GST is charged per line and a discount that never reaches a line cannot reduce it. **Discount reduces tax** decides whether a discount reduces the taxable value — leave it on for a trade discount, turn it off for a settlement discount, which does not reduce GST liability and must still be shown on the invoice.

  All three are **set once**, frozen the same way the base currency is: editable until the branch posts its first sales or purchase document, fixed after that. They started life as configuration keys and were moved — they are structural decisions about how documents are built, not values to be tuned, and they belong beside the other branch-level choices.

- **Journals, the account ledger, opening balances, period locks and the three money screens were unreachable through the gateway.** Their controllers had been added without the matching gateway routes, so every one of those screens worked when a service was called directly and returned "not found" through the front door every deployment actually uses. ### Added
- **Stock adjustments are now a document** — Inventory › Stock adjustments, for a write-off or a physical count. Counting twenty items is one event: it happened on one date, for one reason, and one person authorised it, and recording it as twenty loose movements kept the quantities while losing all three — and left the accounts showing twenty unexplained adjustments where there was one count. A sheet posts as **one document**, so that is what the ledger shows. On a count you key what was actually on the shelf and the difference is worked out for you; **lines that agree are dropped rather than posted as zero**, because on a real count sheet most of them agree. What the system believed at the moment of counting is kept beside what you counted, so the arithmetic can still be checked in six months against the figure that was actually in dispute. A draft holds no number and has moved nothing; posting does both at once, and if any line cannot post — writing off more than is on hand, usually — **nothing on the sheet posts** and no number is spent. There is no void, because the stock physically moved: reversing writes the mirror of the sheet as its own document, dated today, with both keeping their numbers and each pointing at the other. Whoever posts is the approver — the sheet already records who keyed it and who posted it, which is the segregation of duties that matters.
- **Bank statements and reconciliation** — Banking › Statements. Import a **CSV or Excel** statement your bank produced and check it against what you recorded. Every bank lays its export out differently, so you say which column is which once per account and it is remembered — including the two amount layouts (withdrawal and deposit as two columns, or one signed column) and exactly how the date is written, which is read rather than guessed because `03/04/2026` is a real date under three different formats. **Importing the same period again is expected and safe**: every line is recognised by what the bank said about it, so a re-import adds only what is new, and two identical withdrawals on one day are correctly kept as two movements. If the file carries a running balance, the import also checks the bank's own arithmetic — which catches a row that never arrived. Lines with exactly one plausible match are tied up for you; anything less certain is offered as candidates with a reason beside each, because a business paying the same supplier weekly has several identical documents and guessing between them would be a coin toss recorded as a decision. Lines that are not yours can be set aside with a reason, and everything is undoable. **None of it posts to your accounts** — the money already moved and the document that recorded it already posted; reconciling compares the two accounts of the same events rather than producing a third. Export the reconciled statement back out to CSV or Excel for an accountant or a query.
- **⚠ Fixed: Spend money, Receive money and Transfer money were unusable.** All three endpoints would have failed on their first call — a required service was never registered when those screens shipped. Neither the build nor the tests could see it, because the build does not resolve dependencies and the tests build their services by hand. Every service now validates its whole dependency graph at startup, so this class of fault stops the service from starting rather than surfacing as a 500 on the first request.
- **Subledgers now get checked against their control accounts** — Accounting › Opening balances shows it after go-live, and there is a report behind it. Each control account is compared with the sum of the balances beneath it, and the difference is money that belongs to nobody. This is a check double-entry cannot make: a receivable posted to Accounts Receivable with no contact underneath it is a perfectly balanced entry, so the trial balance foots while no one owes the money — the statement is wrong, the aging is wrong, and the first receipt has nothing to settle against. The same check now also runs *before* a migration opens, so a branch whose books are already adrift cannot open on top of it; afterwards nobody could tell which of the two put the difference there.
- **Opening balances** — Accounting › Opening balances, for bringing a branch's books across from whatever it kept them in before: bank and cash balances, every unpaid invoice and bill, and stock on hand. **Receivables and payables come across one line per document, not one per contact and certainly not as a single figure** — each carries the original invoice number and date, because a customer owing across invoices of thirty, ninety and a hundred and eighty days ages nothing like one lump, and an aging report is the first thing anybody opens after a migration. Stock is keyed as a quantity and a **unit cost**, which seeds the item's weighted average and so decides every cost of sale until the next purchase. The panel at the foot shows how far off you still are **as you type**, not when you press the button: every line posts against Opening Balance Equity, so whatever it is left holding is exactly the part of the position not yet keyed, and it reaching nothing is what says the migration is complete. Opening the books is refused until it does — and until every contact named has ledger accounts to receive its balance, and until Inventory confirms the stock it recorded is worth what the document says. If anything is refused, **nothing posts at all** and the whole thing can be retried; a branch that opened with two thirds of its stock is worse than one that did not open, because only the second is obvious. A branch has one opening balance and it cannot be reopened or reversed — an error found afterwards is corrected with a journal entry, which leaves a trail. Migrated fixed assets are not covered yet: they come across as an account balance until the asset register lands.
- **One payment across several bills, and money left over goes somewhere sensible.** A payment is spread by adding a line per document, and each becomes its own pair of ledger entries — so any of the bills can be traced back to the money that cleared it. When the lines stop short of what actually moved, the screen offers to record the remainder as an **overpayment** rather than letting it fold into the settled line: recorded that way it sits in the contact's overpayment balance, visible and refundable on its own, instead of turning their balance the other way up where an aging report reads it as trade. Three things are now refused outright, because each is wrong silently: a line pointing at the wrong kind of document (a bill payment cannot settle an invoice), an advance claiming a document at all, and two lines claiming the same document the same way. Paying a bill and recording an overpayment against that same bill remains perfectly legal — they are different claims. What a document still owes is not yet checked, so nothing stops a line settling more than its bill was for.
- **Foreign-currency bills and invoices now actually clear.** Settling one at a rate that has moved since it was raised clears the balance at the rate it was raised at, moves the bank at the rate you are paying at, and records the difference in **Realized FX Gain/Loss**. Clearing it at today's rate instead would leave the contact carrying a leftover balance against a document they have paid in full — which nobody goes looking for, because the document says settled. Paying a document raised in a different currency from the payment is refused rather than converted, and so is a payment whose original rate cannot be established: "could not check" is not the same as "no difference". No rate is ever looked up live; every one used was recorded on the document it belongs to.
- **Spend money, Receive money and Transfer money** — the three screens for money that moves without an invoice or a bill being raised. A payment is keyed as lines saying what each part of it is for, so paying ₹11,000 against a ₹10,000 bill records ₹10,000 as settling that bill and ₹1,000 as a deposit held with the supplier — and the panel at the foot shows what is still unaccounted for while you type, because unallocated money is usually an overpayment rather than a mistake. **There is no account picker:** the account each line posts to follows from the contact and what the line is for, and the screen shows it rather than asking, so a payment can never land on the control account instead of the contact's own balance beneath it. Drafts are free and unnumbered; a number is taken only when the document posts. A posted document is never edited — void it, and its ledger rows are withdrawn while the document and its number stay. Transfers between your own accounts are a simpler screen again: no contact, nothing to allocate, and a swap button for the two ends.
- **Advances and deposits now have somewhere to sit.** Money that moves before a document exists — a deposit paid to a supplier, a customer's advance, the excess when a payment is rounded up — is now tracked per contact, and kept apart from what is actually owed on invoices and bills. Every contact carries **six** balances rather than two: what they owe you and what you owe them, plus a deposit and an overpayment balance on each side. Deposits and overpayments are held separately rather than pooled, so you can always see which of the two a credit came from. Contacts created earlier pick up the four new balances the next time their branch is set up, and nothing already recorded moves.
- **A payment can now be more than one thing at once.** Paying ₹11,000 against a ₹10,000 bill is a bill payment *and* a deposit: the ledger records ₹10,000 as settling that bill and ₹1,000 as an advance held with the supplier, rather than filing the whole thing under one heading. It matters because a payables report asking for bill payments would otherwise miss the ₹10,000 that genuinely was one — no error, just a total that is quietly short. Refunding a customer's overpayment and refunding a deliberate advance are likewise recorded distinctly, each clearing the balance the money was held in.
- **Journal entries** — Accounting › Journal entries, for the entry you write by hand when no other document fits: an accrual, a correction, a transfer between two accounts. Lines are keyed against any account you are allowed to post to, with debits, credits and the difference between them adding up as you type — an entry is wrong until that difference is nothing, and you can see it before the typing is done rather than after. Save it as a draft as often as you like, unbalanced and unnumbered; a number is taken only when it posts, so an entry you abandon leaves no gap in the sequence. A posted entry is never edited: reverse it, and the offsetting entry stands beside it with both visible and every line paired to the line it cancels. The accounts your invoices, bills and stock movements maintain on their own — receivables, payables, inventory — are kept out of the picker, because a hand entry against one puts it out of step with the ledger behind it and nothing would reconcile the two.
- **Account ledger** — one account over any date range: what it stood at when the range opened, every posting inside it, and a running balance down the page. Each row names the document that wrote it and links straight to it, so any figure can be traced back to what produced it. Credit-balance accounts read the right way up rather than as negative debits.
- **Trial balance** — every account carrying a balance, grouped by account type, with the two column totals at the foot. Those totals agreeing is the single number that says the books are sound, so when they do not the page says so plainly at the top instead of showing a tidy table. Any account name opens its own ledger.
- **Stock now reaches the accounts.** Selling stock posts `Dr Cost of Goods Sold / Cr Inventory` at what the stock cost, so the inventory account and the stock figures agree and gross profit becomes a real number rather than one nobody could compute. Write-offs, shrinkage, returns and opening balances post too; a warehouse transfer posts nothing, because moving stock between your own shelves does not change what you own. Posting runs just behind costing, and every movement carries whether it has reached the books — if one cannot be posted the stock screen says so plainly, because until it is fixed your stock and your accounts disagree. Movements recorded before this release are queued and post at their own dates.
- **Reserved and available stock** — stock promised to a confirmed order is now held back from anything else. The stock list shows reserved and available beside on hand, and a sale is refused when the available quantity is short rather than the on-hand one. Reserving never moves on hand: the goods are still on the shelf and still in the valuation, so counts, stock value and the inventory account read exactly as before. Nothing reserves anything yet — Sales will — so every item currently reads a reserved of nothing.
- **Settings › Organization** — the branch you are signed in to, in three tabs: Profile, Statutory and Financial. TAN, TIN, CIN, Udyam number, website and logo could be set when the account was created and never corrected afterwards; all six are editable now. The GSTIN warns while you type if its first two digits do not match the branch's state, rather than after the save is refused. Base currency is shown but fixed — every posting converts to it.
- **A branch beyond your licence is now created on a 30-day trial** instead of being refused. It is set up and seeded like any other, marked *Trial* in the branch list, and stops on its own date unless a licence is added — your account and your other branches are untouched either way. A branch is a complete set of books, and nobody can judge one without trading a month through it.
- **Each branch has its own end date** — set when the branch is created, taken from your licence at that moment, and checked at every sign-in. It is a cap rather than a replacement: whichever of the branch date and the licence ends first is the one that applies, so a branch can be wound down early without touching the account everyone else works in, and can never outlive the licence paying for it. A closed branch says so by name — your account is unaffected, so there is nothing to renew — and signing out lets you pick another branch. Branches created before this existed have no date of their own and follow the licence exactly as before.
- **Branches** — a Settings screen for the places you trade from. Adding one sets up its books as it is created — chart of accounts, GST rates, numbering series, payment terms, units and purities — and the branch stays marked *Setting up* until that finishes, so it is never handed over half-made. Switch between branches without signing out; you get the permissions you hold in the branch you move to. The number allowed comes from your licence, and the first branch cannot be suspended.
- **Trial signup** — public self-service signup that provisions a customer database, a 14-day Trial licence, the first organization and the owner account, with a progress screen that waits until the account is ready.
- **Two-step login** — sign in once, then choose an organization; skipped automatically when you only have one.
- **Password reset by email code** — a 6-digit code valid for 10 minutes, replacing reset links. Resetting signs out every other session.
- **User invitations** — invited users receive a link and set their own password; no temporary passwords are ever issued.
- **Per-organization currencies** — enable the currencies you trade in, deactivate ones you no longer use, and see only active ones by default. Each currency carries its symbol, format, decimal places and which side the symbol sits on, ready for the amount formatting that reads them.
- **New organizations now arrive set up** — creating one writes its chart of accounts, GST rates, numbering series, payment terms, contact person roles, unit types and units, and metal purities. Previously an organization came up empty, and an item could not be saved at all because saving one requires a unit type. Provisioning now fails and waits for retry rather than handing over an account with no master data.
- **Banks and bank accounts** — each account creates its own account in the chart of accounts automatically, so there is nothing to reconcile by hand between the two. Overdrafts and credit cards are classified as liabilities rather than negative assets. Balances always come from the ledger; nothing is stored twice.
- **Inventory masters** — units, categories, metal purities, warehouses and the item master. Units convert through a single factor to their type's base unit, so kilos and grams are one stock number rather than two; pack sizes are units of their type. An item names its unit type plus its inventory, sales, purchase and report units, with stock and cost always held in the inventory unit.
- **Item profiles** — pharma and jewellery items carry their own tab and their own fields: salt, schedule, storage and minimum expiry on receipt for medicines; metal, purity, weights and making charges for ornaments. Choosing a profile presets the costing method and tracking that vertical needs.
- **Costing method per item** — weighted average, FIFO, LIFO, FEFO or specific identification, fixed once stock has moved because the earlier postings were made under it.
- **Contacts** — one master for customers, vendors, job workers and prescribers, with roles ticked per contact rather than a separate list for each. Addresses, people, bank details, licences and trading limits save together with the contact. GSTIN is checked against the place of supply on save, so a contact cannot be created that would split its tax the wrong way. Every contact gets its receivable and payable sub-accounts automatically.
- **Stock** — quantities and weighted average cost per item, with the full movement history behind them. One pool across every warehouse in the branch: a warehouse says where something moved, never how much sits there. Record openings, receipts, issues, adjustments and warehouse transfers, in whichever unit you counted in — enter 300 grams against an item held in kilos and it converts on the way in, keeping both figures on the record. Stock comes down through a single guarded statement, so two tills cannot both sell the last unit. Selling more than you hold is refused and changes nothing.
- **Costing engine** — what stock cost is now settled just after a sale rather than during it, so a till is never waiting on layer arithmetic. Quantities are still updated immediately and are never wrong; a movement whose cost has not settled says "costing…" rather than showing zero. The stock screen reports when the engine is behind, and anything that fails repeatedly stops and is flagged instead of retrying silently forever. Batch and serial numbers are still checked while you save, because those are yours to correct.
- **Batches, serial numbers and cost layers** — FIFO, LIFO, FEFO and specific identification now mean something. Every receipt records what it cost, and every issue records which receipts it drew from and how much from each, so the cost of a sale can be walked back to the purchases behind it. Batch-tracked items ask for the lot and its expiry, and a lot carries its own printed MRP. Serial-tracked items take one serial per unit, with the BIS HUID held against the piece rather than the design.
- **Backdated receipts restate the sales that came after them** — enter a purchase dated before sales that have already happened and their cost of goods sold is recalculated automatically, because under FIFO that stock should have gone out first. Quantities never change; only what they cost. Each restatement is listed with what the sale cost before, what it costs now, and which receipt caused it. The old figures are kept rather than overwritten.
- **Sales returns go back to the layers they came from** — name the sale being returned and the stock re-enters at the cost it left at, so buying, selling and returning leaves stock value exactly where it started. Partial returns are given back oldest allocation first, and cannot together return more than went out.
- **The item lock is live.** An item's unit type, inventory unit, costing method, profile and tracking options freeze the moment stock first moves, as they were always documented to. Until now nothing had moved, so nothing was ever locked.
- **Vendor payout accounts** — hold several bank accounts against a contact with exactly one default, including UPI ids. Kept separate from your own bank accounts: these are accounts you pay money to, and nothing about them posts to the ledger.
- **Contact licences** — drug licence, FSSAI, BIS and medical registration, each with an expiry. A licence shows as valid, expiring or expired the moment you open the tab, and an expiring-licences report lists everything lapsing across all contacts. Supplying against a lapsed drug licence is an offence, so the date is visible rather than buried.
- **Contact documents** — attach the GST certificate, PAN card, agreements and cancelled cheques to a contact. PDF or image up to 10 MB, with the limit and the accepted types configurable per deployment. Downloads go through the API so another organization can never fetch a file, and removing a document leaves the stored file intact.
- **Contact person roles** — a small master maintained from a popup on the contact list, so a missing role never means abandoning a half-filled contact. Reorderable by drag; built-in roles can be renamed but not deleted.
- **Payment terms** — Due on Receipt, Net 15/30/45/60 and End of Month out of the box, plus your own. Supports early-payment discounts, and shows the due date each term produces for a bill dated today so "end of month plus 15" is unambiguous.
- **Numbering series** — a Settings screen that defines how every generated code is built: prefix, financial-year segment, branch code, zero padding and suffix, with a live preview. Series reset yearly, monthly or daily on your financial year, can differ per branch, and are reorderable by drag. Document series are held to consecutive numbering, so a number is taken at save rather than when the form opens and cannot be typed by hand. Customer, vendor, item, warehouse and bank series are created with every new organization.
- **Documentation site** — this help app, versioned alongside the product.
- **Roles & permissions** — the five built-in roles now carry their actual permission grants, and you can create your own roles with a per-module permission matrix. Built-in roles can be renamed to suit your vocabulary without changing what they allow.
- **Configuration screen** — edit unit-price and quantity decimal places and default payment terms per organization, with a one-click reset back to the shipped default.
- **Email settings** — configure the mailbox invitations and verification codes are sent from, with a test-send button to confirm the credentials before relying on them. A customer can send from its own address instead of the platform default.
- **User management** — invite people by email with a role, resend an invitation, and revoke access. Invitations are links, so nobody is ever sent a temporary password.
- **Chart of accounts** — a per-organization chart grouped by account type, seeded with ten standard accounts when the organization is created. Accounts carry usage flags controlling which document pickers they appear in, and can be renamed freely; once an account has been used its type and code are fixed so existing postings cannot be reclassified.
- **An item can be given its HSN code and GST rate.** Both were on the item all along and reachable from no screen, so nothing could be taxed. The General tab now has a code picker — search by code or description, goods offered HSN and services SAC — and a rate beside it. Choosing a code pre-selects the rate it usually attracts, but never replaces one you have already set, because the same code is rated differently by condition.
- **HSN & SAC codes** — a searchable screen under Settings for the goods and services codes, filterable to goods or services and paged fifty at a time. It is read-only: the codes are national and shared by every business on the platform, so they are maintained centrally from the official CBIC list rather than per account. The screen reports how much of the list is loaded, so an empty search reads as data not yet imported rather than as a broken search.
- **Tax master** — the six standard GST rates are created with each organization, including the 3% bullion rate. Enter a total and the CGST, SGST and IGST split fills itself in. Rates are effective-dated: changing one creates a new version and keeps the old, so invoices dated before the change still use the rate that applied then.
- **Sub-accounts** — per-contact, per-item and per-tax-rate detail beneath the control accounts, provisioned automatically by the master that owns them. GST rates get separate CGST, SGST and IGST sub-accounts in each direction, so tax reports break down by rate and component.
- **Sub-accounts screen** — see what is posting beneath each control account, grouped by account and filtered by owner type. Read-only: sub-accounts belong to the contact, item or tax rate that created them.
- **Development, Staging, UAT and Production environments** — every service and both Angular apps now build and run against a named environment. Development works from a fresh clone with no setup; the other three take their connection strings, signing keys and service addresses from the deployment environment, and refuse to start rather than fall back to a local default. Web and Docs can each be debugged in Development or Staging from VS Code.

### Fixed
- **Two sign-in endpoints accepted requests with no credentials at all.** Reading the branches you may work in, and switching between them, were both callable by anyone who could reach the service — a blanket exemption added for the sign-in pages had silently overridden their own checks. Both require a valid session again.
- **The More menu and the contact-roles popup could not be closed from the keyboard.** Both opened as an overlay you dismissed by clicking outside, with no key that did the same thing, so a keyboard user who opened either was stuck in it. Escape now closes both.
- **A branch created before a default existed could never receive it.** Setting up a branch wrote its GST rates, numbering series, payment terms, contact person roles, units and metal purities only if it had none at all, so anything added to those lists afterwards reached new branches and no others — the 3% bullion rate would have reached only branches created after it was added. **Finish setup** now adds just the missing rows and can be pressed at any time, including on a branch that is already complete, where it does nothing. Rows are matched on their internal name rather than their label, so a term you renamed is not handed back to you a second time under its original wording, and nothing you added yourself is touched. Two cases are deliberately skipped instead of forced: a shipped default whose name you have already used for something of your own, and a unit type whose base unit you have changed, where the shipped conversion factors no longer apply.
- **Generated numbers used April as the financial year start for every branch**, whatever the branch was actually set to. A branch on a calendar year was issued `INV/2526/…` when it should have had `INV/2025/…`, and its yearly counters restarted in the wrong month — silently, since nothing about the number looks wrong until an auditor asks. Both the generated number and the preview on the Numbering series screen now use the branch's own setting.
- **A contact could be saved without its ledger sub-accounts and nothing said so.** The failure was silently discarded, leaving a contact that looked complete and could not be invoiced. Contacts now show **No sub-ledger** when that has happened, with a **Link sub-ledger** action to create them — the same treatment a bank account whose ledger link failed already had.
- Contacts, Inventory and Banking could not start in Development at all: none of them had a development configuration, so each refused to boot on a missing token signing key. All three now start from a fresh clone.
- An account that already had sub-accounts beneath it could still have its type, code and usage flags changed. The configuration lock now engages the moment anything is created under an account, as it was always documented to.
- Changing the currency of a locked account appeared to save but silently did nothing. It is now refused with an explanation, alongside the other frozen fields.
- An account could be made its own ancestor through a chain of parents, producing a chart of accounts that no report could total. Parent changes now reject cycles.

### Security
- **The menu shows only what your role can open.** Entries for modules you have no access to are no longer drawn, and a bookmark or typed address for one of their screens lands on Home instead of a page that fails as it loads. The server checks every request regardless — this is about not offering what you cannot have.
- **Roles finally decide what you can do.** Every permission you assign has been recorded on the sign-in token since the beginning and checked by nothing — so whatever role someone held, they could reach any screen and change anything on it. Each screen now asks for the permission it needs: reading asks for `.view`, changing for `.edit`, deleting for `.delete`, against the module that owns the data rather than the menu the screen sits under. Nobody gains access; some roles lose access they were never meant to have.
- **Accountant and Sales gained read-only access to what their jobs need.** Enforcing the matrix for the first time showed two built-in roles could not work: Sales could not open the item master or stock, and Accountant could not open contacts or inventory. Both now read those screens and still cannot change them. Adjust it on a copy of the role if that is not how your business runs.
- **Every service-to-service endpoint is now behind the shared key.** Seven of the ten were not: creating an owner account, reading a customer's database connection, resolving an organization's licence, provisioning ledger sub-accounts, sending mail and importing the HSN/SAC list could all be called by anything that could reach the port. They now require the same key the seeding endpoints already did, and every service both sends and checks it.
- **Signing in is required by default.** Each service now refuses an unauthenticated request unless the endpoint says otherwise, rather than allowing one unless somebody remembered to add a check. Only sign-in, signup and the country and state lists the signup form needs are open, and they say so explicitly. Reference data that is not secret but is nobody else's business — currencies, HSN/SAC codes, account and ledger types — is no longer served without a token.
- **Branch settings can only be read and changed from inside that branch.** A branch's currencies and configuration took the branch from the URL with nothing checking it against who was asking, so any signed-in user could name another branch's id and read or edit it. Both now refuse unless the branch you are signed in to is the one in the address. Mail settings are the same for the account, and the platform's own mailbox now needs an operator permission rather than any account at all.
- **Branch isolation is now enforced by the database for the chart of accounts, sub-accounts and tax rates.** Those three were the last tables relying on the application alone to keep one branch's rows out of another's. They now carry the same row-level security policy every other table already had, so the boundary holds however the data is reached.
- Trial expiry pauses access without locking you out of your account: you can still sign in, see why access stopped and renew. Feature pages and their APIs both refuse access until the licence is renewed.
- Password reset never reveals whether an email address is registered.

### Changed
- **⚠ Breaking — a branch is now an organization.** The model is two levels, not three: your **customer account is the head office**, and each **organization is a branch**. The separate branch list has been removed — it duplicated the organization almost field for field, while only the organization ever separated any data. Each branch keeps its own items, contacts, stock, chart of accounts and numbering, so nothing leaks between them. Warehouses and numbering series no longer ask which branch they belong to, because the branch you are signed in to is the answer. Organizations now carry a short branch code, used in generated document numbers; existing organizations are set to `HO`.
- Licence tiers are Trial, Standard, Pro and Elite. Tier and state are tracked separately, so an Elite plan that lapses reports as expired without losing its tier.
- Invitation and verification emails now send in the background and retry automatically, so saving an invitation no longer waits on the mail server.
- Account types are now the only level above the chart of accounts; account sub-types were removed. Accounts carry a contra flag directly, and an account can be renamed for display without changing what it is.

## Versioning

Semantic versioning. **Major** for a breaking change to the API or data model, **minor** for new capability, **patch** for fixes.

Releases are cut from `main`; the version in `package.json` and the heading here must match.
